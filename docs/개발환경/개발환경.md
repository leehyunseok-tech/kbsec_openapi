# 개발 환경

## Python 버전 관리 / 가상환경

- 패키지 관리자로 **uv**를 사용한다. (프로젝트 전용 가상환경 격리, 빠른 설치 속도, `pyproject.toml` 기반 의존성/lock 관리)
- 설치 방법(Windows): `winget install --id=astral-sh.uv -e`
- 프로젝트 루트에서 `uv init`으로 초기화함. 아래 파일들이 생성됨.
  - `pyproject.toml` — 프로젝트 메타데이터 및 의존성 목록
  - `.python-version` — 프로젝트가 사용할 Python 버전 고정 (현재 `3.11` — 아래 "지원 Python 버전 하향" 절 참고)
  - `main.py` — 진입점 예시 파일
  - `.venv/` — 이 프로젝트 전용 가상환경 (git에는 커밋하지 않음, `.gitignore`에 포함됨)
- `uv init`은 git 저장소가 없으면 자동으로 `git init`도 수행한다.

## 패키지 설치/관리

- 패키지 추가: `uv add <패키지명>` (예: `uv add openpyxl`)
- 개발 전용 도구 추가: `uv add --dev <패키지명>` — `[dependency-groups] dev`에 들어가며 런타임 의존성과 분리된다(현재 `ruff`).
- 패키지 제거: `uv remove <패키지명>`
- 의존성 동기화(가상환경에 lock 파일 기준으로 설치): `uv sync`

## 지원 Python 버전 하향 (3.14 → 3.11)

- 원래 `uv init` 기본값 그대로 `requires-python = ">=3.14"` / `.python-version = 3.14`였다. 하지만 3.14는 2025-10 릴리스라 **공개 저장소 기준으로는 대부분의 사용자가 설치 단계에서 막히는** 제약이었다.
- 실제로 3.12+/3.13+/3.14 전용 문법(PEP 695 `type` 별칭, `except*`, `@override` 등)과 표준 라이브러리 API(`itertools.batched`, `datetime.UTC`, `tomllib` 등) 사용처를 전수 검색한 결과 **0건**이었다. 코드가 쓰는 가장 최신 문법은 `X | None`(3.10+)뿐이라, 코드 수정 없이 하한만 낮출 수 있었다.
- 그래서 `pyproject.toml`의 `requires-python`과 `.python-version`을 모두 **3.11**로 낮췄다. `.python-version`까지 함께 낮춘 이유는, 이 값이 uv가 가상환경을 만들 때 쓰는 기본 버전이라 3.14로 두면 3.11 사용자도 3.14를 새로 내려받게 되어 하향의 의미가 사라지기 때문이다.
- 하향 후 `uv sync`로 lock을 3.11 기준 재해석하고, `compileall`과 전체 모듈 import로 정상 동작을 확인했다. CI(`.github/workflows/ci.yml`)가 **3.11/3.12/3.13 세 버전에서 import를 검증**하므로, 이후 누군가 3.12+ 전용 문법을 넣으면 즉시 실패한다.

## 코드 품질 도구 (ruff) / CI

- 린터·포매터는 **ruff 하나로 통일**했다(별도 black/isort/flake8 없음). 설정은 `pyproject.toml`의 `[tool.ruff]`이며 `line-length = 120`, 규칙은 `E`(pycodestyle) `F`(pyflakes) `I`(isort) `UP`(pyupgrade) `B`(bugbear) `C4` `SIM`을 켰다.
- 끈 규칙은 이유를 함께 적어 둔다 — `E501`(줄 길이는 포매터가 담당, 한글 주석이 많아 강제 줄바꿈이 오히려 나쁨), `generate_mst.py`의 `C408`(CURATION 표는 `dict(seq=1, ...)` 키워드 형태여야 표처럼 읽힘), `src/run/*.py`·`manage/generate/*.py`의 `E402`(stdout 인코딩 재설정·sys.path 부트스트랩을 import보다 먼저 해야 함).
- 초기 도입 시 126건이 검출되어 62건은 자동 수정, 나머지는 개별 판단으로 처리했다. 이 중 **의미가 바뀌면 안 되는 두 가지**는 그대로 두고 의도를 주석으로 남겼다:
  - `direct_api_command.py`의 `zip(fields, args, strict=False)` — 인자를 필드 수보다 **적게** 주는 것이 정상 동작(나머지는 공백 유지)이라 `strict=True`를 넣으면 기능이 깨진다.
  - `investor_command.py`의 `NamedTemporaryFile(delete=False)` — 경로만 얻어 matplotlib이 쓰게 한 뒤 호출자가 전송할 때까지 파일이 살아 있어야 하므로 컨텍스트 매니저를 쓰면 안 된다.
- **자동 생성 코드도 lint/format 대상이다.** 문자열 조립으로 코드를 찍어내면 들여쓰기·빈 줄이 포매터 기준과 미세하게 어긋나는데, 템플릿을 손으로 맞추는 대신 `generate_api_client.py`가 **생성 직후 자기 산출물에 `ruff format`을 실행**하도록 했다(codegen → format 패턴). 덕분에 재생성해도 CI가 깨지지 않는다. 생성 코드에서 lint 오류가 나면 파일이 아니라 **생성기 템플릿을 고친다**(실제로 `registry.py`의 `if/else` → 삼항, import 묶음 형태를 이렇게 고쳤다).
- `ruff format` 전체 적용은 3,000줄 규모라 `git blame`을 가리므로, 해당 커밋 해시를 `.git-blame-ignore-revs`에 등록했다. 로컬 적용은 `git config blame.ignoreRevsFile .git-blame-ignore-revs` (GitHub 웹 blame은 자동 인식).
- CI는 `.github/workflows/ci.yml`의 4개 잡: ① ruff check + format --check ② 3.11/3.12/3.13 문법·import 검증 ③ **생성 코드 최신성**(재생성 후 `git diff`가 나면 실패 — 명세만 고치고 재생성을 깜빡한 경우를 잡는다) ④ 웹 JS `node --check`. CI에는 `config/config.py`가 없으므로(gitignore) 각 잡이 `config.example.py`를 복사해 쓴다 — import 검증만 하므로 실제 API 호출은 일어나지 않는다.

## 런타임 상태 파일의 원자적 쓰기 (src/utils/json_store.py)

- `config/data/*.json`(설정 `settings.json`, 예약 `schedules.json`, 쿨다운 `cooldown_log.json`)은 원래 각 매니저가 `Path.write_text(json.dumps(...))`로 직접 덮어썼다. 여기엔 두 가지 실제 위험이 있었다:
  1. **비원자적 쓰기** — `write_text`는 파일을 먼저 비우고 다시 쓰므로, 도중에 프로세스가 죽거나 디스크가 차면 잘린 JSON이 남아 다음 로드가 실패한다. 감시목록이 날아가면 자동매매가 조용히 멈춘다.
  2. **락 부재로 인한 lost update** — `load_settings()` → 수정 → `save_settings()` 사이에 다른 스레드가 끼어들면 나중 쓰기가 앞선 변경을 덮어쓴다. brk/wave/grid 모니터가 각자 데몬 스레드에서 감시목록을 갱신하고(`brk_monitor.py`, `grid_monitor.py`, `wave_monitor.py`) 웹은 다중 사용자가 같은 파일을 공유하므로 **실제로 발생 가능한 조합**이었다.
- 이를 `src/utils/json_store.py` 한 곳으로 모아 해결했다. `write_json()`은 같은 디렉터리에 임시 파일로 쓰고 `flush`+`fsync` 후 `os.replace()`로 교체한다(같은 파일시스템 내 원자적 교체 — 어느 시점에 죽어도 "이전 내용" 또는 "새 내용"만 남고 잘린 중간 상태가 없다). `update_json()`은 읽기-수정-쓰기 전체를 파일별 `threading.RLock`으로 감싼다.
- `settings_manager.py`/`schedule_manager.py`/`cooldown_log.py`가 모두 이 모듈을 경유하도록 바꿨고, `SettingsManager.update_settings(mutate)`를 추가해 lost update가 우려되는 자리에서 읽기-수정-쓰기를 한 번에 처리할 수 있게 했다.
- 검증: 8스레드 × 200회 동시 증가(총 1,600회)에서 **유실 0건**, 손상된 JSON 파일에서 기본값 복구, 임시 파일 잔존 0건을 실제로 확인했다.
- **한계(문서화된 제약)**: 락은 프로세스 내부 동기화다. 텔레그램 봇과 웹 서버를 별도 프로세스로 띄우면 프로세스 간 lost update는 여전히 가능하며, 그 경우 파일 락(fcntl/msvcrt)이나 SQLite로 옮겨야 한다. 다만 **원자적 쓰기 덕분에 파일이 깨지는 일은 프로세스가 몇 개든 발생하지 않는다.**

  - (참고: `docs/api/명세`, `docs/api/명세_md` 폴더는 각각 `docs/api/xlsx`, `docs/api/md`로 이름이 변경됨 — 한글/공백 경로가 일부 도구에서 인식되지 않는 문제 때문으로 보임)

- 생성 결과:
  - `docs/api/api-list.md` — AI가 읽기 쉬운 표 형태의 전체 API 목록

- `docs/api/md` 파일이 추가/변경되면 스크립트를 다시 실행해 목록을 갱신한다.

## API 클라이언트 코드 생성

- KB증권 REST API를 실제로 호출하는 파이썬 코드는 `manage/generate/generate_api_client.py`가 `docs/api/md/*.md`의 "## INPUT" 표까지 파싱해 자동 생성한다.
- 실행: `uv run python -m manage.generate.generate_api_client`
- 생성 결과 (수동 수정 금지, 재실행 시 덮어써짐):
  - `src/api/price_info.py`, `src/api/rank_info.py`, `src/api/chart.py`, `src/api/stock_info.py`, `src/api/market_info.py`, `src/api/investor_chart.py`, `src/api/order.py`, `src/api/reserve_order.py`, `src/api/account.py`, `src/api/withdraw.py` — 카테고리별 모듈, 함수 1개 = API 1개 (예: `src.api.order.ssam1801(...)`), 코드 배정 규칙은 스크립트의 `CODE_TO_MODULE` 딕셔너리 참고.
  - `src/api/registry.py` — API 코드 → 함수 매핑 (`REGISTRY`), `terminal.py`의 `call <코드>` 명령이 여기서 함수를 찾는다.
- 수기 작성 파일(생성 대상 아님): `src/api/client.py`(공용 요청 봉투/호출 로직), `src/api/auth.py`(토큰 발급).
- 인증: `config/config.py`에 실제 KB 개발자포털 발급 `real_client_key`/`real_client_secret`을 채운 뒤 `uv run python -m src.run.terminal`에서 `login real` → `call <코드> '<json>'`으로 테스트. **KB증권 개발환경(모의투자)은 아직 제공되지 않아 운영환경(`real`)만 사용 가능** — `dev_client_key`/`dev_client_secret`/`login dev` 코드 경로는 남아있지만 현재는 정상 동작하지 않는다.

  - `docs/mst/md/openapi_mst_*.md` — 선별표의 마크다운 판 + 코드→라벨 변환 규칙

## 텔레그램 Agent / AI 자연어 / 자동매매

- 텔레그램 Agent·AI 자연어 변환·자동매매 전략을 제공한다. 전체 기능 목록은 `docs/features.md` 참고.
- `src/run/telegram.py` — `TelegramBot`, 텔레그램 폴링 기반 운영 클라이언트. `src/run/terminal.py` — `TerminalClient`, 동일한 `src/commands/*.py` 핸들러를 공유하는 터미널 클라이언트(듀얼 클라이언트 아키텍처).
- KB API에는 실시간 웹소켓이 없어, 실시간 시세가 필요한 기능(트레일링 스탑/자동손절)도 `src/utils/monitor_base.py`(`MonitorBase`) 기반 REST 폴링으로 구현했다. 평가손익은 `SSQM2952`(잔고현황 조회)의 `val_yld` 필드를 그대로 사용.
- AI 자연어 변환(`src/utils/ai_command_converter.py`)은 `docs/command_guide_for_ai.md`를 시스템 프롬프트에 그대로 삽입한다 — **명령어 추가/변경 시 반드시 `docs/command_guide_for_ai.md`도 함께 갱신**해야 한다(`CLAUDE.md` 필수 규칙).
- 조건검색식 실시간거래(jggs/cond)·VI감시·테마분석·공매도분석은 KB API 74개 중 대응 API가 없어 미지원.
- `config/config.py`에 `telegram_token`/`telegram_chat_id`(Agent용), `claude_api_key`/`claude_model`(자연어 변환용, 선택) 추가됨.

## 웹 인터페이스 (FastAPI + 순수 HTML/JS)

- 세 번째 클라이언트로 웹 브라우저 인터페이스를 추가함 (트리플 클라이언트: 텔레그램 `telegram.py` / 터미널 `terminal.py` / 웹 `src/web/`).
- 기술 스택: 백엔드는 **FastAPI + uvicorn**(순수 JSON API, `src/web/app.py`), 프론트엔드는 **서버 템플릿(Jinja2 등) 없이 순수 HTML+CSS+JS(fetch)** (`src/web/static/`) — 외부 JS 라이브러리/CDN 의존 없음.
- 실행: `uv run python -m src.run.web` 또는 `manage/run/run-web.bat`/`manage/run/run-web.sh` → http://localhost:8000 접속. 호스트/포트는 `KBSEC_WEB_HOST`(기본 `127.0.0.1`)/`KBSEC_WEB_PORT`(기본 `8000`) 환경변수로 변경.
- **다중 사용자 구조**: 브라우저 쿠키(`kbsec_web_sid`) 하나당 `WebClient` 인스턴스 하나(`src/web/session_store.py` 인메모리 매핑). 터미널/텔레그램과 달리 config.py의 앱키로 자동 로그인하지 않고, 각 사용자가 설정 화면에서 자기 client_key/client_secret(필수), Claude/텔레그램 키(선택)를 입력한다. 입력값은 서버 메모리에만 보관되고 파일로 저장하지 않으며, 서버 재시작 시 재입력 필요.
- 이 작업을 위해 기존 코드에 다중 인스턴스 대응 개선을 함께 적용함:
  - `handle_brk`/`handle_wave`/`handle_grid`에 `monitor=None` 인자 추가 — 전역 싱글턴(`set_*_monitor`)만 쓰면 웹에서 마지막 접속 사용자의 모니터가 전체를 가로채는 문제가 있어, 웹은 자기 모니터를 명시적으로 넘긴다(telegram/terminal은 기존 전역 방식 그대로).
  - `convert_natural_to_commands`/`send_photo`/`send_document`에 키·토큰 override 인자 추가(생략 시 config.py 전역값 — 기존 동작 불변).
- **알려진 제약**: 설정값·자동매매 감시목록(`config/data/settings.json`)은 `SettingsManager`가 파일 하나에 저장하므로 웹 사용자 전원이 공유한다(화면·README에 안내됨).

### 접속 관문 — HTTP Basic Auth (클라우드 배포 대비)

- 웹 화면 자체(정적 파일+`/api/*` 전체)는 기본적으로 접근 인증이 없다 — KB 계좌 로그인(설정 화면에서 앱키 입력)과는 별개로, "이 서버 URL을 누가 열어볼 수 있는가"를 막는 장치가 없었다는 뜻. 로컬(`127.0.0.1`) 전용으로 쓸 때는 문제없지만, 클라우드 등 외부에 노출하려면 이 관문이 필요하다.
- `src/web/app.py`에 `basic_auth` 미들웨어를 추가해 `KBSEC_WEB_BASIC_AUTH_USER`/`KBSEC_WEB_BASIC_AUTH_PASS` 환경변수를 **둘 다** 설정하면 브라우저 표준 HTTP Basic Auth 팝업이 전체 경로 앞을 막도록 구현함(`secrets.compare_digest`로 타이밍 공격 방지). 하나라도 비어 있으면(기본값) 지금까지와 동일하게 관문 없이 동작 — 로컬 개발 편의를 해치지 않는 opt-in 설계.
- **config.py 폴백**: 환경변수가 없으면 `config.py`의 `web_basic_auth_user`/`web_basic_auth_pass`를 대신 읽는다(`_env_or_config()` 헬퍼, `_configured()`로 placeholder `"YOUR_..."` 제외). 매번 터미널에서 `$env:`를 치지 않고 로컬에서 계속 켜두고 쓰고 싶은 사용자를 위한 대안 — 환경변수가 있으면 그쪽이 항상 우선한다(클라우드 systemd 배포 시 서비스 파일에서 주입하는 방식과 자연스럽게 공존).
- nginx 등 리버스 프록시를 새로 배우지 않고도(별도 설치 없이) 이 프로젝트 코드만으로 최소한의 접근 통제를 걸 수 있도록 하기 위한 선택. 다만 HTTPS가 없으면 Basic Auth 자격증명이 평문으로 오가므로, 외부 공개 시에는 TLS를 적용하는 리버스 프록시나 신뢰 네트워크(VPN, SSH 터널 등)와 함께 쓰는 것을 권장한다.
- **버그 수정**: `secrets.compare_digest`의 `str` 버전은 non-ASCII(한글 등)를 지원하지 않아 `TypeError`로 500 에러가 났다 — 한글 포함 테스트 자격증명(`config.py`에 `테스트아이디`/`테스트비번`으로 채워 검증하는 과정에서 발견)으로 실제로 재현했고, 양쪽을 `.encode("utf-8")`로 바이트 변환 후 비교하도록 고쳐 해결했다.
- 검증(2026-07-20): 로컬에서 ① 환경변수 미설정+config.py 미설정 시 기존과 동일하게 인증 없이 200 응답 ② `config.py`에만 한글 자격증명(`테스트아이디`/`테스트비번`) 설정 시 자동으로 관문이 켜짐(자격증명 없음/틀림 → 401, 올바른 UTF-8 인코딩 헤더로 → 200) ③ `/`(정적)과 `/api/commands`(API) 양쪽 모두 동일 적용 확인. (참고: Windows curl의 `-u` 옵션은 한글을 UTF-8이 아닌 로컬 코드페이지로 인코딩해 보내 서버와 안 맞는 자격증명처럼 401이 나는 환경 문제가 있었다 — `Authorization` 헤더를 파이썬으로 직접 UTF-8 base64 인코딩해 재현/검증함. 서버 로직 자체의 문제는 아니었지만, Basic Auth 자격증명은 도구 간 인코딩 차이를 피하려면 영문/숫자로 쓰는 것이 가장 안전하다.)

## 설치 스크립트 (manage/install/install-project.bat / manage/install/install-project.sh)

> 원래 프로젝트 루트에 있었으나(`install-project.bat`/`.sh`), `run-*`/`manage/generate/`의 다른
> 관리 스크립트들과 함께 `manage/install/`로 이동함 — 상세는 `docs/개발환경/manage.md` 참고.
> 이동에 맞춰 스크립트 내부 `cd`도 프로젝트 루트까지 두 단계 되짚어가도록(`%~dp0..\..` /
> `$(dirname ...)/../..`) 수정됨.

- GitHub에서 신규 클론한 환경을 원샷으로 세팅하는 스크립트. Python만 사전 설치되어 있으면 나머지는 자동:
  1. Python 존재 확인 — 없으면 https://www.python.org/downloads/ 링크를 안내하고 종료 (Windows는 Microsoft Store 별칭 stub도 미설치로 판정됨).
  2. uv 확인/자동 설치 — Windows: winget 우선, 실패 시 공식 PowerShell 인스톨러 폴백 + 현재 세션 PATH에 설치 경로(`%USERPROFILE%\.local\bin`, WinGet Links) 추가. macOS/Linux: curl(또는 wget)로 공식 인스톨러 + `$HOME/.local/bin` PATH 추가.
  3. `uv sync` — `.venv` 생성 및 uv.lock 기준 의존성 전체 설치. `.python-version`(3.14) 고정 버전이 시스템에 없으면 uv가 자동 다운로드.
  4. `config/config.py`가 없으면 `config.example.py`를 복사해 생성(있으면 건드리지 않음 — 멱등).
  5. (sh만) `manage/run/run-*.sh`에 실행 권한 부여.
- 완료 후 `config/config.py`에 실제 키만 채우면 `manage/run/run-*.bat`/`manage/run/run-*.sh`가 바로 동작한다.
- 메시지 언어는 기존 스크립트 관례를 따름: `.bat`는 영문(cp949 콘솔 한글 깨짐 방지), `.sh`는 한글.

### 루트 대표 진입점: `install-kbsec-openapi.bat` / `install-kbsec-openapi.sh`

- 신규 클론 사용자가 `manage\install\install-project.*` 경로를 몰라도 되도록 프로젝트 루트에 둔 얇은 대표 스크립트. 하는 일은 단 두 가지뿐이다: ① `manage/install/install-project.bat`/`.sh`를 그대로 호출 ② **설치가 성공(종료 코드 0)하면 어느 쪽을 실행했든 `install-kbsec-openapi.bat`와 `.sh` 둘 다 삭제**한다. 실패하면 재시도할 수 있도록 둘 다 삭제하지 않고 남겨둔다 — 한쪽만 지워지는 경우는 없다(성공 시 항상 둘 다, 실패 시 항상 둘 다 유지).
- **커밋 대상**(위의 `run-kbsec-openapi.bat`/`.sh`와 반대 — 그쪽은 설치 시점에 생성되는 gitignore 로컬 산출물). 정상 설치를 마친 로컬 작업 트리에는 이 두 파일이 없는 게 정상 상태이고, 그 상태에서 `git status`는 둘 다 "deleted"로 표시한다 — 새 클론/원격 저장소에는 그대로 남아 있으므로 되살리거나 재커밋할 필요가 없다.
- Windows(`.bat`)는 실행 중인 배치 파일이 자신을 직접 지울 수 없는 제약 때문에, 짝인 `.sh`는 `del /f /q`로 즉시 지우고 자기 자신(`.bat`)만 `start "" /b cmd /c del "%~f0"`로 별도 프로세스를 백그라운드로 띄워 원본 프로세스가 종료돼 파일 잠금이 풀린 뒤 삭제되도록 구현했다(Windows 배치의 표준 자기 삭제 관용구). macOS/Linux(`.sh`)는 실행 중인 스크립트도 `rm`으로 지울 수 있어 `.bat`/`.sh` 둘 다 한 번에 `rm -f -- "$SCRIPT_DIR"/install-kbsec-openapi.{bat,sh}`로 지운다(별도 트릭 불필요).
- 설치 성공/실패 여부는 `manage/install/install-project.bat`/`.sh`의 종료 코드로 판단한다(`call`/`if errorlevel 1`(bat), `if bash ...; then`(sh)) — 그 스크립트의 각 실패 분기(Python 미설치, uv 설치 실패, `uv sync` 실패)는 이미 `exit /b 1`/`exit 1`로 끝나므로 별도 수정 없이 그대로 감지된다. 두 스크립트 모두 성공/실패 4가지 조합(`.bat` 성공/실패, `.sh` 성공/실패)을 스텁 설치 스크립트로 실제 실행해 둘 다 지워지는지/둘 다 남는지 검증함.
- 저장소의 다른 `.sh`(`manage/run/*.sh`, `manage/install/install-project.sh`)와 동일하게 실행 권한 없이(모드 `100644`) 커밋되어 있다 — 설치 전 진입점이라 `install-project.sh`의 `chmod` 단계에 의존할 수 없어서(닭이 먼저냐 달걀이 먼저냐), macOS/Linux에서는 README 안내대로 최초 1회 `chmod +x install-kbsec-openapi.sh`를 직접 실행해야 한다.

## 실행 스크립트 (manage/run/*.bat, *.sh)

> 원래 프로젝트 루트에 있었으나(`run-main.*`/`run-terminal.*`/`run-web.*`), 관리 스크립트를
> 한 곳에 모으면서 `manage/run/`으로 이동함 — 상세는 `docs/개발환경/manage.md` 참고. 이동에
> 맞춰 내부 `cd`도 프로젝트 루트까지 두 단계 되짚어가도록 수정됨(아래 서술은 대부분 이동
> 이전 작성 당시 그대로 두되, 현재 경로로 갱신함).

- 루트가 아니라 `manage/run/`에 OS별로 분리된 실행 스크립트가 있다. **`*.bat`는 Windows 전용, `*.sh`는 macOS/Linux 전용**이며 서로 대체 불가(둘 다 같은 OS에서 동작하는 게 아니라 각자 자기 OS에서만 씀).
  - `manage/run/run-telegram.bat`(Windows) / `manage/run/run-telegram.sh`(macOS·Linux) — 텔레그램 Agent(`src/run/telegram.py`) 실행
  - `manage/run/run-terminal.bat`(Windows) / `manage/run/run-terminal.sh`(macOS·Linux) — 터미널 클라이언트(`src/run/terminal.py`) 실행
  - `manage/run/run-web.bat`(Windows) / `manage/run/run-web.sh`(macOS·Linux) — 웹 클라이언트(`src/run/web.py`, uvicorn) 실행
- 내부적으로 `uv run python -m src.run.telegram`/`uv run python -m src.run.terminal`을 호출하므로 가상환경을 미리 activate하지 않아도 된다. 스크립트는 `manage/run/`에서 프로젝트 루트로 두 단계 위로 `cd`하므로(`%~dp0..\..` / `$(dirname ...)/../..`) 어느 위치에서 실행하든 동작한다. `-m` 모듈 실행 방식을 쓰는 이유는 아래 "소스 레이아웃(src/)" 참고.
- macOS/Linux에서는 최초 1회 `chmod +x manage/run/run-telegram.sh manage/run/run-terminal.sh`로 실행 권한을 부여해야 한다(`install-project.sh`를 실행했다면 자동으로 부여됨). Windows(`*.bat`)는 별도 권한 설정이 필요 없다.
- (참고) 최초 작성 시엔 `main.bat`/`client.bat`처럼 접두어 없는 이름이었으나, 두 스크립트가 무엇을 실행하는지 이름만으로 더 분명하도록 `run-` 접두어를 붙여 `run-main.*`/`run-client.*`로 리네임함. 이후 파일 자체(`cli_client.py`)도 `terminal.py`로 이름을 바꾸면서 스크립트도 `run-terminal.*`로 다시 리네임함. 이후 `main.py`/`terminal.py` 자체가 `src/run/`으로 옮겨가며 실행 방식도 `python <파일>` 직접 실행에서 `python -m src.run.<모듈>` 모듈 실행으로 바뀜. 훨씬 뒤에 `run-*.bat`/`.sh` 자체도 프로젝트 루트에서 `manage/run/`으로 이동함(위 안내 박스 참고). 그 뒤 통합 런처(`run-kbsec-openapi`)의 인자 `main`이 텔레그램과의 연결을 이름만으로 알기 어렵다는 이유로, `src/run/main.py`→`src/run/telegram.py`, `manage/run/run-main.*`→`manage/run/run-telegram.*`, 런처 인자 `main`→`telegram`으로 다시 리네임됨(관련 import·문서·설치 스크립트 전체 동기화).

## 소스 레이아웃 (src/)

- `src/` 폴더를 만들어 실행 코드를 한 군데로 모음: `utils/` → `src/utils/`, `api/` → `src/api/`, `telegram/` → `src/messenger/`(파이썬 표준 라이브러리에는 없지만 PyPI의 유명 `python-telegram-bot` 패키지와 이름이 겹치는 걸 피하려고 `messenger`로 개명), `main.py`/`terminal.py` → `src/run/`.
- `config/`, `docs/`, `logs/`는 이동하지 않고 프로젝트 루트에 그대로 둔다 — `config/config.py`는 gitignore 대상 실제 키 파일이라 소스 트리와 분리해두는 편이 안전하고, `docs/`는 코드가 아닌 문서/명세 자산이기 때문.
- 모든 임포트를 절대경로 `from src.utils...`/`from src.api...`/`from src.msgr...`/`from src.commands...` 형태로 통일함(당시 예시는 `src.messenger`였으나 이후 `src.msgr`로 리네임됨 — 아래 "메신저 폴더 리네임" 절 참고). `src/run/telegram.py`·`src/run/terminal.py`는 `uv run python -m src.run.telegram`처럼 **모듈(`-m`) 방식으로만 실행**한다 — 프로젝트 루트를 `sys.path`에 올려야 `src.*` 절대 임포트가 풀리기 때문에, `python src/run/telegram.py`처럼 파일 경로로 직접 실행하면 `ModuleNotFoundError: No module named 'src'`가 난다. `manage/run/run-telegram.*`/`manage/run/run-terminal.*` 스크립트가 이 호출 방식을 감싸고 있으니 일반적으로는 스크립트만 쓰면 된다.
- `src/`, `src/run/`에도 기존 `utils/`·`api/`·`telegram/`과 동일하게 `__init__.py`를 둔다(빈 패키지 마커).
- 파일 내부에서 `Path(__file__).resolve().parent...`로 프로젝트 루트(설정/로그/문서 경로)를 계산하던 곳은 모두 한 단계 더 깊어진 경로에 맞춰 `.parent`를 하나씩 추가함 — 예: `src/utils/*.py`는 `parent.parent`→`parent.parent.parent`.
- `docs/api/generate_api_client.py`(코드 생성 스크립트)의 출력 경로도 `PROJECT_ROOT / "api"` → `PROJECT_ROOT / "src" / "api"`로 갱신함. 당시엔 이 스크립트를 `docs/api/`에 그대로 뒀으나(이동 대상 아님), 이후 `docs/`의 다른 관리 스크립트들과 함께 `src/manage/`로, 다시 프로젝트 루트의 `manage/generate/`로 재이동함 — 상세는 `docs/개발환경/manage.md` 참고.

### 후속 조정: `commands/`를 `messenger/`에서 분리 (멀티 메신저 대비)

처음엔 `telegram/commands/` → `src/messenger/commands/`로 옮겼으나, 사용자가
"앞으로 텔레그램뿐 아니라 다른 메신저도 붙일 예정"이라고 밝혀 구조를 한 번 더 조정함:

- `src/messenger/commands/` → `src/commands/` — 명령 핸들러(`handle_login`, `handle_buy` 등)는 텔레그램 전용이
  아니라 `main.py`/`terminal.py`가 공통으로 호출하는 메신저 무관 로직이라, `messenger/` 밑이 아니라 `src/` 바로
  아래(`api/`·`utils/`·`run/`과 나란히)로 옮기는 게 실제 역할에 맞음.
- `src/messenger/tel_send.py`/`tel_receive.py` → `src/messenger/telegram/tel_send.py`/`tel_receive.py` — 텔레그램
  Bot API 전송계층만 `telegram/` 하위 패키지로 한 단계 더 감싸둠. 나중에 디스코드/슬랙을 추가하면
  `src/messenger/discord/`, `src/messenger/slack/`처럼 나란히 추가하면 됨. 공통 인터페이스(추상 베이스 클래스 등)는
  아직 만들지 않음 — 실제 두 번째 메신저를 붙일 때 두 구현을 보고 공통점을 뽑는 게 더 정확해서 지금은 폴더
  구조만 미리 자리를 잡아둔 상태.

### 후속 리네임: `src/messenger/` → `src/msgr/`

위 절의 `messenger`라는 이름은 폴더가 처음 자리 잡을 당시의 실제 이름이라 그대로 남겨뒀지만,
**이후 `src/msgr/`로 다시 리네임되어 현재는 `src/messenger/`가 존재하지 않는다.** `git mv src/messenger
src/msgr`로 폴더 자체를 옮기고, `src/run/main.py`·`src/web/client.py`의
`from src.messenger.telegram...` import를 `from src.msgr.telegram...`으로 갱신했다(하위
`telegram/` 패키지 이름과 그 안의 `tel_send.py`/`tel_receive.py`는 그대로 유지 — 바뀐 건
바깥쪽 메신저 총괄 폴더 이름뿐). 위 "후속 조정" 절이나 이 문서 상단의 예시 임포트에 남아있는
`src.messenger`/`src/messenger` 표기는 그 시점 기준 역사적 사실이므로 고치지 않았다 — 현재
경로를 참조할 때는 항상 `src/msgr/`를 기준으로 할 것.
- 파일이 한 단계 얕아진 `src/commands/log_command.py`는 `Path(__file__)` 루트 계산도 `.parent`를 하나 줄임
  (`parent.parent.parent.parent` → `parent.parent.parent`, `src/utils/*.py`와 동일한 깊이).

## 경로 상수 모듈 (src/paths.py)

- 여러 모듈이 각자 `Path(__file__).resolve().parent...`로 프로젝트 루트를 독립 계산해
  참조 파일 경로(`docs/command_guide_for_ai.md`, `mst/api/*.mst`, `config/data/*.json`,
  `logs/` 등)를 하드코딩하던 구조를 정리 — **`src/paths.py` 한 곳에 경로 상수를 모으고
  14개 모듈(src 10곳 + manage/generate 4곳)이 전부 여기서 import 하도록 전환**했다.
- 위 "소스 레이아웃" 절의 "루트 계산 `.parent`를 하나씩 추가" 방식은 이 전환으로
  폐지됨 — 이제 모듈 깊이가 바뀌어도 개별 파일의 경로 계산을 손볼 일이 없다.
- `manage/generate/*.py`는 파일 직접 실행(-m 없이)도 지원하기 위해 import 전에
  sys.path 부트스트랩(`sys.path.insert(0, str(PROJECT_ROOT))`)만 자체 유지하고,
  경로 조합은 전부 `src.paths` 상수를 쓴다.
- 새 참조 파일을 추가하거나 참조 파일을 옮길 때의 절차는 `docs/개발환경/paths.md` 참고
  (원칙: 파일 이동 시 `src/paths.py` 한 줄만 수정, 새 경로 하드코딩 금지).
